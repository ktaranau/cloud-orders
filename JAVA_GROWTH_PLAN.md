## 1. Что есть сейчас

**Сделано хорошо (это реальная база, не переделываем):**

- Spring Boot 4.1.1 / Java 21, слои controller/service/repository, DTO-records, constructor injection, транзакции.
- PostgreSQL + Flyway, `ddl-auto=validate`, `open-in-view=false`.
- Testcontainers, 42 теста, GitHub Actions CI, работа через ветки и PR.
- JWT Resource Server, scopes read/write, Keycloak с воспроизводимым импортом realm.
- Compose с healthcheck, readiness с проверкой БД, эксперименты с отказом БД и таймаутами HikariCP.

**Где проблема:**

| Наблюдение | Почему это важно |
| --- | --- |
| За ~2,5 месяца занятий: 1 таблица, 3 эндпоинта, ~12 классов | Глубина высокая, но охват стека маленький |
| 7 из 9 занятий посвящены Security/Keycloak | Для собеседования на Java backend это уже больше, чем обычно спрашивают |
| Kafka в плане Codex прямо отложена («одна очередь SQS достаточно») | Kafka встречается в Java-вакансиях намного чаще SQS, и это твой запрос номер один |
| NoSQL в плане нет вообще (ни Redis, ни MongoDB, ни DynamoDB) | Второй пункт твоего запроса не покрыт |
| AWS: только IAM/SSO и разбор инцидента с KMS, ни одного развёртывания | Третий пункт запроса стоит в самом конце маршрута |
| Работа стоит с 24 октября: PR #7 локально выглядит неслитым, урок 9 не начат | Потерян темп |
| Процесс очень церемонный: длинные конспекты, протокол каждой проверки | Много времени уходит на отчётность, а не на новый материал |

**Вывод:** фундамент годный, но маршрут ведёт к роли «человек, который эксплуатирует один сервис в AWS», а тебе нужен профиль Java backend-разработчика: Spring + SQL + Kafka + кеш/NoSQL + облако + наблюдаемость. Маршрут нужно развернуть в ширину.

## 2. Главные изменения курса

1. **Kafka вместо SQS как основная очередь.** Запускается локально и бесплатно (Compose, KRaft, Testcontainers). SQS остаётся короткой сравнительной лабораторией в блоке AWS.
2. **Добавляем NoSQL:** Redis обязательно, MongoDB как read-модель; DynamoDB коротко в блоке AWS.
3. **Закрываем Security.** Урок 9 делаем в сокращённом виде и останавливаемся. Модель владения заказами откладываем: она потребует пользовательского login flow и съест ещё месяц.
4. **Расширяем домен.** На одной таблице без изменений состояния нельзя показать ни события, ни блокировки, ни N+1. Нужны позиции заказа, смена статуса и второй сервис.
5. **Таймбокс на тему.** 1-3 недели на блок, потом идём дальше, даже если остались «недоказанные» мелочи. Они записываются в backlog, а не блокируют.
6. **AWS: сначала LocalStack, потом одна короткая настоящая лаборатория** с заранее посчитанной ценой и удалением в тот же день.
7. **Kubernetes в минимальном объёме в конце** (kind локально). Он есть почти в каждой вакансии, полностью пропускать нельзя; EKS не трогаем.

## 3. Маршрут

Расчёт на 2-3 занятия в неделю по 60-90 минут. Всего около 16 недель, то есть до середины марта 2027.

### Фаза 0. Закрыть хвосты (до 1 недели)

- Проверить привязки портов, слить PR #7, обновить main.
- Урок 9 в коротком варианте: класс `KeycloakContractTests`, намеренная регрессия, PR. Без повторного конспекта.
- Мелкая уборка одним PR: `HELP.md` → `README.md`, убрать дублирующий `application.yaml`, пустые теги в `pom.xml`.

### Фаза 1. Домен и данные (2 недели)

- `OrderItem` (one-to-many), миграции V2+, N+1 и способы лечения (fetch join, entity graph, проекции).
- Смена статуса: `POST /orders/{id}/pay`, `/cancel`, правила переходов, 409 при недопустимом.
- `@Version` и потерянное обновление: воспроизвести тестом с двумя потоками.
- Пагинация и сортировка, индексы, `EXPLAIN ANALYZE`, уровни изоляции.
- Ошибки в формате `ProblemDetail` (RFC 9457) вместо самодельного `ApiError`; обработка неверного JSON/UUID.

*Результат:* можешь объяснить N+1, optimistic locking, изоляцию транзакций и показать это в коде.

### Фаза 2. Kafka (3-4 недели) — главный блок

- Kafka в Compose (KRaft). Топики, партиции, ключи, порядок, consumer groups, offsets, rebalancing.
- Сервис публикует события `OrderCreated/Paid/Cancelled`. Сначала наивно, затем увидеть проблему dual write и сделать **transactional outbox**.
- Второй сервис (`notification-service` или `payment-service`): `@KafkaListener`, ручной/автоматический commit, at-least-once.
- Идемпотентный consumer, retry с backoff, dead letter topic, poison message.
- Тесты с Testcontainers Kafka; Awaitility вместо sleep.
- Эволюция схемы события: JSON с версией; Avro + Schema Registry как необязательное продолжение.
- Сюда же встраиваем часть многопоточности: concurrency consumer'ов, virtual threads, ограничение параллелизма.

*Результат:* отвечаешь на вопросы про гарантии доставки, порядок, дубликаты, outbox, и у тебя два сервиса, общающихся через Kafka.

### Фаза 3. Redis и NoSQL (2 недели)

- Redis: cache-aside для чтения заказа, TTL, инвалидация при смене статуса, `Idempotency-Key` для POST, простой rate limit.
- MongoDB: отдельная read-модель «история заказа», которую строит consumer из Kafka. Моделирование документа против реляционной схемы, индексы, когда что выбирать.

*Результат:* объясняешь стратегии кеширования и их риски, отличия документной модели, базовый CQRS.

### Фаза 4. Взаимодействие сервисов и наблюдаемость (2 недели)

- Синхронный вызов между сервисами: `RestClient`, таймауты, retry, circuit breaker (Resilience4j).
- Micrometer + Prometheus/Grafana, структурированные логи, correlation ID через HTTP и Kafka-заголовки, трассировка OpenTelemetry.
- Dockerfile: non-root, layered jar, лимиты памяти, graceful shutdown.
- Небольшая нагрузка (k6 или Gatling): p95, пул соединений, thread dump/JFR.

### Фаза 5. AWS (3 недели)

- LocalStack + AWS SDK v2: S3 (выгрузка заказов), SQS (сравнение с Kafka), DynamoDB (сравнение с MongoDB), Secrets Manager.
- Terraform на LocalStack: state, plan, модули.
- Настоящая лаборатория на 1-2 вечера: ECR → ECS Fargate + RDS, GitHub OIDC без постоянных ключей, откат версии, `terraform destroy` и проверка остатков. Цена считается заранее; MSK и NAT Gateway не используем.

### Фаза 6. Kubernetes-минимум и упаковка (1-2 недели)

- kind: Deployment, Service, ConfigMap/Secret, probes (они уже есть), rolling update, лимиты.
- README со схемой, 4-5 коротких ADR (outbox, кеш, read-модель, выбор очереди), запуск одной командой.
- Пробные собеседования: Java core/concurrency, Spring, SQL, Kafka, system design на примере своего проекта.

## 4. Как работаем

- **Код пишешь ты, я ревьюю и объясняю.** Готовое решение даю, только если просишь или тема чисто инфраструктурная.
- **Короткий формат занятия:** цель → механизм на 5-10 минут → задача → ты делаешь → ревью PR → 3-5 вопросов «как на собеседовании».
- **Конспект = README и ADR в самом репозитории**, а не длинные файлы уроков рядом. Так материал сразу становится портфолио.
- **Один PR = одно законченное поведение**, как и сейчас. Это работает, оставляем.
- **В конце каждой фазы:** список вопросов собеседования по теме и твои ответы своими словами.
- Правила про расходы AWS и `docker compose down -v` из старого плана сохраняем.

## 5. Замечания по текущему коду

Не срочно, закрываются по ходу фаз:

- `Dockerfile`: запуск от root, нет layered jar и настроек памяти (фаза 4).
- `OrderService.getAll()` читает всю таблицу (фаза 1).
- `OffsetDateTime.now()` прямо в сервисе: внедрить `Clock` для тестируемости.
- Нет `@Version`, индексов, связей между сущностями (фаза 1).
- `GlobalExceptionHandler` покрывает только валидацию и 404; остальные ошибки отдаются в другом формате.
- Одновременно `application.properties` и `application.yaml`.
- `OrderStatus.PAID/CANCELLED` объявлены, но недостижимы.
